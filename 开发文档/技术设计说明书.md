## 1. 目标与边界

系统支撑无人值守健身房：手机号注册、人脸入库、选店、购卡、微信支付、闸机认脸进店、门店服务。私教课包、加盟整页按需求分期，表结构和模块预留，不在第一期做完。

已确认、覆盖旧方案的三点：

1. 用户用手机号登录。首次注册必须上传一张正脸，照片通过大小检查后签发正式登录态和会员编号。购卡后才把照片下发到本店闸机。
2. 闸机只做人脸识别。小程序不提供开门码，后端不签发进店二维码。
3. PC 管理端分总账号和门店账号。总账号看全部门店，门店账号只看绑定的那一家店。

四条边界：

1. 小程序、管理端、闸机只访问同一个后端，不互相直连数据库。
2. 支付密钥、会员是否有效、夜班电话判断、人脸是否已入库，只存在于服务端。
3. 闸机按厂商 HTTP 和 WebSocket 对接，长连接路径 `/ws/gate`。不另做门店适配进程，也不接人脸云。
4. 教练不单独做小程序。后期以同一小程序的角色区分。课时码如果做，只扣课，不能进店。

## 2. 总体架构

```
微信小程序 (uni-app)          PC 管理端 (Vue 3)
        \                         /
         \                       /
          Nginx  HTTPS / 已备案域名
                    |
            Spring Boot 单体
         手机号登录  人脸入库  门店  卡种
         订单  支付  会员权限  闸机验权
         账号数据范围  内容配置  工单  文件
              |            |
           MySQL 8       Redis 7
              |
           对象存储（人脸照片私有，厂商未定）

注册成功 → 人脸下发闸机/厂商
闸机认脸成功 ----HTTP 验会员----> Spring Boot
（可选）厂商 SDK 适配进程 --HTTP--> 同上验权接口
```

采用模块化单体，不拆微服务。门店数量和开门 QPS 在单店几十人、连锁几十到上百家时，一台应用加 MySQL、Redis 足够。拆服务会把支付回调、库存、会员生效拆到多个事务里，得不偿失。

逻辑分层（每个业务模块内部遵守）：

| 层 | 职责 |
| --- | --- |
| interfaces | HTTP 控制器、入参校验、出参组装。分 mp、admin、gate、pay-notify |
| application | 用例：手机号注册、人脸入库、下单、支付成功履约、验脸开门 |
| domain | 卡种是否可买、会员天数、权限是否有效。不依赖 Spring Web |
| infrastructure | MyBatis、Redis、微信支付 SDK、COS、微信登录 HTTP |

依赖方向：interfaces → application → domain，infrastructure 实现 domain 需要的端口。控制器不直接改数据库。

## 3. 技术选型

版本写到一代即可。初始化项目时锁定该代的当前稳定补丁，并写入各工程的锁文件。

### 3.1 后端

| 类别 | 选型 | 用途 |
| --- | --- | --- |
| 语言 | Java 17 | 微信支付官方 SDK 与后续闸机 JVM 适配都使用这一代 |
| 框架 | Spring Boot 3.5.x | Web、校验、事务、配置 |
| Web | spring-boot-starter-web | REST |
| 校验 | spring-boot-starter-validation | 入参 |
| 安全 | Spring Security | 小程序令牌、管理端令牌、闸机签名分过滤器 |
| ORM | MyBatis-Plus 3.5.x | 业务 CRUD。复杂更新（库存、履约）写显式 SQL |
| 迁移 | Flyway | 表结构版本化，禁止手改生产库 |
| 数据库 | MySQL 8.0，InnoDB，utf8mb4 | 业务数据 |
| 缓存 | Redis 7，Spring Data Redis | 登录令牌、进店防抖、课时码、接口限流、支付通知去重 |
| 连接池 | HikariCP | Boot 默认 |
| 支付 | wechatpay-java（微信支付 APIv3 官方 SDK） | 下单、回调验签、关单、退款 |
| 对象存储 | 厂商未定后再选 SDK | 指引图、报修图、器械视频 |
| API 文档 | springdoc-openapi + Knife4j 4.x | 仅 dev、test 暴露 |
| 工具 | Lombok、MapStruct | 样板代码、对象转换 |
| 日志 | Logback，生产 JSON | 带 traceId |
| 测试 | JUnit 5、Spring Boot Test | 履约、库存、验码单测 |

不引入：Dubbo、Nacos、Kafka、Elasticsearch、独立网关、单独的文件服务进程。公告和工单用 MySQL 即可。量上来再加消息队列。

金额使用「分」的 `BIGINT`，禁止 `double` / `float`。对前端的 JSON 数字若可能超过 `2^53-1`（雪花 ID），一律用字符串。

### 3.2 微信小程序

| 类别 | 选型 | 用途 |
| --- | --- | --- |
| 框架 | uni-app Vue 3 + TypeScript，Vite 版 CLI | 只编译到微信小程序 |
| 状态 | Pinia | 登录态、当前门店 |
| 请求 | 封装 `uni.request` | 统一错误码、登录失效 |
| 地图 | 微信小程序 `<map>`（即腾讯地图） | 门店地图 |
| 导航 | `uni.openLocation` | 调起腾讯地图导航 |
| 定位 | `uni.getLocation` | 算距离。距离由服务端用坐标重算 |
| 支付 | `uni.requestPayment` | 只提交服务端返回的支付参数 |
| 客服 | `button open-type="contact"` | 进入微信客服会话，不自建 IM |
| 扫码 | `uni.scanCode` | 只扫器械二维码。团购核销是手输。进店不扫码 |
| 人脸采集 | `camera` 拍照 | 现场正脸，不从相册选。仅注册流程使用 |
| 手机号 | `getPhoneNumber` | 微信手机号快速验证 |
| 电话 | `uni.makePhoneCall` | 客服电话 |

小程序限制及对应做法：

| 限制 | 做法 |
| --- | --- |
| 只能请求已配置的 HTTPS 合法域名 | request、uploadFile、downloadFile 三个域名都配到 API 与 COS |
| 不能在端上保存支付私钥 | 下单、签名、回调全在 Spring Boot |
| 主包 2MB，总包 20MB | 图片走 COS 网络地址，不打进包体。指引图、器械视频不放本地 |
| 无长期后台任务 | 人脸只在注册时采集一次。进店由闸机完成，不靠小程序停留在前台 |
| 支付结果以回调为准 | 用户从收银台返回后，前端再查一次订单，避免回调稍晚 |

协议勾选后的约 4 秒倒计时只做在前端，用来挡住连点。服务端不认倒计时，只检查「这笔下单带了已发布的协议版本号」。

## 5. 部署架构

### 5.1 环境

| 环境 | 用途 |
| --- | --- |
| local | 这台不能装 Docker 的电脑用。Spring Boot 用内嵌 H2（文件在 `code/server/data`），登录令牌放进程内存，不连接 MySQL 和 Redis |
| dev | 本机已有 Docker 时使用。Compose 起 MySQL 8 和 Redis 7，登录令牌放 Redis。手机号、图片上传、地图选点仍用和 `local` 相同的测试实现，不需要微信、对象存储和腾讯地图的密钥。闸机协议已接上，没有实机时用管理端模拟验码 |
| test | 云主机。微信支付用沙箱或小额真实商户。小程序用体验版 |
| prod | 上传到服务器的正式版本。独立 MySQL、独立 Redis、独立商户号与 COS 桶 |

换到可以安装 Docker Desktop 的电脑后，用 `dev` 接 Compose 里的 MySQL 和 Redis。本地哪些是测试数据、怎么启动，见 `开发文档/调试文档.md`。线上密钥和闸机配置见 `开发文档/发布文档.md`。

这台不能装 Docker 的电脑看效果：

1. 后端在 `code/server` 启动，必须带 local：`mvn spring-boot:run -Dspring-boot.run.profiles=local`
2. 管理端在 `code/admin` 执行 `npm run dev`，打开 `http://localhost:5173`。总账号 `admin` / `admin123`
3. 小程序用微信开发者工具导入 `code/mp/dist/build/mp-weixin`（只看现成页面不必一直开着编译命令）。勾选不校验合法域名。请求地址是 `http://127.0.0.1:8080`

`local` 的数据只在这台电脑上。重启后端后已登录的管理端要重新登录。不能开两个后端实例。

**正式版本上传服务器时必须改回来，不能带 local。** 启动参数改为 `prod`（环境变量 `SPRING_PROFILES_ACTIVE=prod`），并配好 `application-prod.yml` 里的 `MYSQL_*`、`REDIS_*`。服务器上如果仍是 local，数据写在应用目录的 H2 文件里，令牌在内存中，重启即失效，也不能水平扩展。`application.yml` 的默认 profile 仍是 `dev`，不会自动变成 local；漏改时去核对服务器进程的启动参数，确认不是 `local`。

dev、test、prod 的小程序 AppId、商户号、回调地址、COS 桶互不混用。`local` 和 `dev` 打开模拟支付，按钮「模拟支付成功」走和微信回调相同的履约。`prod` 关闭模拟支付，必须走微信支付。

管理端的 Banner、门店封面、到店指引可以手填图片网址，也可以点「上传」选本地图片。`local`、`dev` 和自动化测试把文件写在 `code/server/data/public`，接口返回 `http://127.0.0.1:8080/uploads/...`，小程序直接用这个地址显示。**正式版本不能再这样。** 上传服务器后，同一接口要改成把图片传到对象存储，数据库里只存网址，应用服务器不再对外提供 `/uploads/`。腾讯云或阿里云还没选定，选定前 `prod` 会直接拒绝上传，避免图片写进服务器磁盘。对应实现是 `PublicImageStorage`：`LocalPublicImageStorage` 用在 `local`、`dev`、`test`，`prod` 上的实现目前只负责拒绝。

管理端新增和编辑门店可以在地图上选点，自动填写省、市、地址和经纬度。库存坐标是国测局坐标 GCJ-02，和小程序 `<map>`、`openLocation` 一致。`local`、`dev` 和自动化测试用 OpenStreetMap 的 Nominatim 解析地址，不需要地图 Key。**正式版本不能再这样。** 上传服务器后要配置环境变量 `TENCENT_MAP_KEY`（腾讯位置服务 WebService Key），由 `TencentPlaceLookup` 解析。`prod` 下如果没配这个 Key，选点会直接拒绝。手机号登录：`local`、`dev`、`test` 用测试手机号，`prod` 才接微信。人脸不接云厂商，购卡后下发到闸机。

### 5.2 生产拓扑（一期）

```
用户手机 ──443──> Nginx
                    ├─ /            管理端静态文件
                    ├─ /api/        反代 Spring Boot :8080
                    └─ 证书（小程序要求合法 HTTPS）

Spring Boot ──> 云 MySQL
            ──> 云 Redis（仅内网）
            ──> COS
            ──> api.mch.weixin.qq.com

闸机（门店网络）──443──> 同一 /api/gate/
```

应用至少两个实例时，会话不放本机内存。登录态在 Redis，因此可以直接水平扩展。一期单实例即可，结构上不阻碍加实例。人脸照片在 COS，不放本机磁盘。

微信支付回调 URL 必须是外网 HTTPS，且在商户平台配置。闸机如果只在店内网，由门店路由访问公网 API，不把 MySQL 端口暴露给门店。

## 6. 安全

| 对象 | 机制 |
| --- | --- |
| 小程序用户 | 手机号验证通过且人脸入库成功后，才签发正式 JWT。有效期 2 小时，刷新令牌 14 天，放 Redis，可作废。只完成手机号时签发 `scope=FACE_ENROLL` 的临时令牌，只能调用人脸上传 |
| 管理员 | 账号密码（BCrypt）签发另一套 JWT。密钥与用户令牌分开。密码错误次数 Redis 计数，10 分钟 5 次锁定。令牌内带角色和 `storeId` |
| 闸机 | 厂商协议走 WebSocket `/ws/gate` 和 `/api/v1/verify_user`。总账号可启用签名口令。管理端模拟验码仍用设备 `secret` 做 HMAC |
| 支付回调 | 只认微信支付平台证书验签。验签失败直接 401，不改订单 |
| 管理端数据范围 | 总账号不加门店条件。门店账号的每条查询和导出都强制 `store_id = 令牌中的门店`。请求里带了别的门店 ID 直接 403 |
| 人脸照片 | COS 私有目录。日志不打印照片地址上的签名。门店账号接口不返回照片。总账号查看照片写审计日志 |
| 传输 | 全站 HTTPS。Redis、MySQL 仅内网 |
| 上传 | 服务端签发 COS 临时上传凭证，文件不经应用服务器中转。人脸只接受现场拍摄后的上传 |
| 敏感输出 | WiFi 密码接口必须注册成功。日志里手机号打码，禁止打印支付私钥、JWT、WiFi 密码、人脸文件内容 |
| 越权 | 订单、报修、投诉、课时按 `user_id` 查询。不信任客户端传来的用户 ID |

管理端角色只有两种：

| 角色 | 令牌 | 范围 |
| --- | --- | --- |
| 总账号 `MASTER` | `storeId` 为空 | 全部门店的会员、订单、进店记录、工单、在线情况、设备，以及门店、卡种、协议、支付、账号 |
| 门店账号 `STORE` | `storeId` 必填 | 只能看这一家店。可设置本店电话、到店指引、卡种和价格，可处理本店报修、投诉、失物。不能改协议、支付、店名和营业状态，不能创建总账号，不能看全品牌汇总 |

一个门店可以有多个门店账号。一个门店账号只绑定一家店。停用账号时删除其刷新令牌。

小程序用户没有后台那种 RBAC。状态是：未注册、待采集人脸、已注册无有效会员、当前门店有效会员。业务接口认正式令牌，注解用 `@MpLogin`、`@MpMember`。`@MpLogin` 拒绝 `FACE_ENROLL` 临时令牌。

## 7. 接口规范

### 7.1 路径

| 前缀 | 调用方 | 认证 |
| --- | --- | --- |
| `/api/mp/**` | 小程序 | 用户 JWT。浏览类接口在白名单 |
| `/api/admin/**` | 管理端 | 管理员 JWT |
| `/api/gate/**` | 闸机或适配进程 | 设备签名 |
| `/api/pay/wechat/notify` | 微信支付 | 平台证书验签，无 JWT |

统一前缀后面再加版本意义不大，用路径模块名即可，例如 `/api/mp/stores`、`/api/mp/orders`。

### 7.2 响应

```json
{
  "code": 0,
  "message": "ok",
  "data": {},
  "traceId": "b7e1..."
}
```

`code = 0` 成功。HTTP 状态：参数错误 400，未登录 401，无权限 403，业务拒绝 200（体里带业务码），系统故障 500。业务拒绝用 HTTP 200 是为了小程序 `uni.request` 始终走 success 回调，由封装层按 `code` 提示。闸机验码例外：网络失败与业务拒绝都要有稳定 JSON，闸机按 `data.open` 判断，不解析 HTML。

分页：`page` 从 1，`pageSize` 默认 20，最大 100。响应 `{ list, total }`。

时间：ISO-8601 本地偏移，如 `2026-10-08T19:17:00+08:00`。

金额：请求和响应都用「分」的整数。展示层再换成元。

### 7.3 错误码

| 区间 | 含义 |
| --- | --- |
| 0 | 成功 |
| 40000–40099 | 参数 |
| 40100–40199 | 未登录或令牌失效 |
| 40300–40399 | 无权限。含门店账号访问其他店、未购卡却被闸机请求开门 |
| 41000–41099 | 卡种不可买、库存不足、协议版本过期 |
| 42000–42099 | 订单与支付 |
| 43000–43099 | 人脸未入库、识别结果对不上会员、会员无效、设备未登记 |
| 44000–44099 | 团购券 |
| 50000 | 未分类服务器错误。消息用「系统繁忙」，原始异常只进日志 |

禁止把数据库异常、`请求参数错误` 这类框架原文返回给小程序。

### 7.4 幂等

| 场景 | 做法 |
| --- | --- |
| 创建支付订单 | 请求头 `Idempotency-Key`。同一用户、同一键 10 分钟内返回原订单 |
| 支付回调 | `transaction_id` 唯一索引。重复通知只应答成功 |
| 闸机验权 | 同一人、同一闸机、15 秒内的重复识别合并成一条进店流水，仍返回 `open=true` |
| 工单提交 | 可选幂等键，避免弱网双提交 |

### 7.5 小程序白名单（无需登录）

- 门店列表、门店地图数据、门店公开信息（不含 WiFi 密码、不含在线人数）
- 卡种列表（只读展示，下单需注册成功）
- Banner、公告、加盟介绍页内容
- 协议正文
- 建立微信会话、提交微信手机号凭证

购卡下单、团购核销、WiFi、报修、投诉、失物、订单，都要正式登录（人脸已入库）。注册过程中的人脸上传只接受临时令牌。

## 8. 认证流程

### 8.1 小程序登录与人脸注册

用户看到的是手机号登录。`wx.login` 仍要做，只为拿到 `openid`，供微信支付使用，这一步不叫登录成功。

```
wx.login 取得 code
  → POST /api/mp/auth/session { code }
  → jscode2session 换 openid、session_key，建立未完成注册的会话
用户点击手机号快捷登录
  → POST /api/mp/auth/phone { phoneCode }
  → 服务端向微信换手机号
  → 该手机号已是 ACTIVE：签发正式 accessToken，进入首页
  → 否则：写入手机号，状态改为 NEED_FACE，签发 scope=FACE_ENROLL 的临时令牌
拍摄正脸（禁止相册）
  → POST /api/mp/face
  → 照片存入服务端私有目录，小于 32 字节要求重拍
  → 成功：状态改为 ACTIVE，分配会员编号，临时令牌换成正式令牌
  → 失败：保持 NEED_FACE，返回可重拍的原因
购卡成功后，再把这张照片下发到本店闸机
```

会员编号在照片通过大小检查时生成，不依赖购卡。使用数据库序列，展示为 9 位数字字符串。没买会员的人有编号，但闸机里没有这张脸，不能进店。

`session_key` 只留在服务端 Redis，不发给前端。正式接口一律拒绝临时令牌。

已注册用户再次进入只走手机号。更换人脸会再拍一张，已购本店会员的用 `editUser` 覆盖闸机上的同一会员编号。

### 8.2 管理端登录与数据范围

`POST /api/admin/auth/login` 账号密码。令牌内含 `adminId`、`role`（`MASTER` 或 `STORE`）、`storeId`（门店账号必填）。

所有 `/api/admin/**` 查询经统一的数据范围：

- `MASTER`：可按请求里的 `storeId` 筛选，不传表示全部店。
- `STORE`：忽略客户端传来的其他门店，固定用令牌里的 `storeId`。客户端若显式传了不匹配的门店，返回 403，避免静默看错店。

列表、详情、导出、工单处理都走这一层。只在前端隐藏菜单不算完成。

### 8.3 当前门店

小程序本地记住 `currentStoreId`。服务端每个写操作自己接收 `storeId` 并校验门店存在且上架。切换门店不调用“绑定用户”接口，避免和「购卡后不能改店」混淆。不能改的是已支付订单和会员权限上的门店，不是浏览用的当前门店。

## 9. 核心流程

### 9.1 购卡与支付

```
选卡
  → GET 卡种（含 purchasable、lockText、剩余张数）
  → 前端展示确认层与协议
  → POST /api/mp/orders
       body: storeId, cardProductId, agreementId, agreementVersion
  → 服务端校验：登录、卡可买、库存、协议是当前发布版、门店一致
  → 写订单 PENDING，限量卡占用 1 个库存
  → 调微信 JSAPI 下单
  → 返回 orderId 与 wx.requestPayment 所需字段
  → 用户支付或取消
  → 微信支付异步通知
  → 验签、金额核对、幂等履约：订单 PAID，库存转为已售，写入会员权限
```

补充规则：

- 订单 15 分钟未支付，定时任务关单：调微信关单、订单变 `CLOSED`、释放占用库存。
- 用户取消支付：前端 `POST /api/mp/orders/{id}/cancel`。若微信侧已支付而本地误取消，以回调为准把订单改回已支付并履约。
- 履约与改订单状态在同一数据库事务。事务提交后再删缓存。
- 支付描述使用「{门店名}-{卡名}」。收银台顶部的商户名称来自商户号简称，不是接口随便填的店名。一期一个商户号；`store.mch_id` 列先留空，以后一店一商户再启用。
- 前端从收银台返回：`GET /api/mp/orders/{id}`。状态已支付则进入结果页，未支付则提示可继续付。结果页文案按「支付成功，会员已生效」做，需求未规定更多字段。

### 9.2 人脸进店

小程序不参与开门。人走到闸机前即可。现行协议见 `需求/闸机对接.md`，实现状态见 `开发文档/闸机对接开发设计.md`。

```
购卡成功
  → 服务端经 WebSocket /ws/gate 把正脸和到期时间下发到本店闸机
闸机摄像头比对本地人脸
  → 认不出：门不开，可上报 /api/v1/stranger，服务端记未开门
  → 认出会员编号
  → POST /api/v1/verify_user
  → 设备已登记、未停用，且该店会员未过期
  → 返回 Result=0，闸机开门，服务端写成功流水
```

没买会员的人脸不会下发，闸机认不出，不能进店。过期或非本店会员不开门。同一用户、同一闸机、15 秒内再次识别不再插第二条成功流水，仍然开门。

管理端没有实机时，仍可用旧的 `POST /api/gate/v1/verify` 做模拟验码。厂商闸机不调用这个地址。

课时码使用 `lesson:qr:`，只给教练核销。闸机不接受课时码。

### 9.3 团购核销

```
POST /api/mp/groupon/redeem { storeId, platform, code }
  → 券码格式校验、限流（同一用户每分钟 5 次）
  → 调对应平台核销接口（美团 / 抖音 / 大众点评）
  → 按券规则表得到 cardProductId
  → 与支付成功相同的履约方法写入会员权限
  → 记核销流水
```

平台接口的密钥和门店映射放管理端配置。一期可以先做「手输券码 + 管理端人工确认」的内部核销，平台 API 证书齐了再接自动核销。两种方式写入同一个履约方法，避免两套会员逻辑。

好评赠卡是核销之后的领取记录，表分开。赠送天数未定时，领取接口先不在 P0 打开。

### 9.4 上传

```
POST /api/mp/files/presign { biz: FACE|REPAIR|COMPLAINT|LOST, contentType }
  → 返回 COS 临时上传 URL 与 objectKey
  → 客户端直传
  → 提交工单时只传 objectKey
```

服务端校验 objectKey 前缀属于该用户当次签发的目录。人脸图限制 5MB，且 `FACE` 前缀只有临时令牌或正式用户本人能提交。工单图片限制 5MB，视频（器械库，管理端上传）限制 200MB。人脸提交后还要走第 8.1 节的厂商入库，只上传到 COS 不算注册成功。

### 9.5 客服电话时段

`GET /api/mp/stores/{id}/contacts` 由服务端按 `Asia/Shanghai` 当前时间过滤：

- 落在白班：返回白班号码列表。
- 落在夜班：返回夜班号码。
- 夜班未配置号码：返回 `nightAvailable=false` 与文案「不在夜班时间，请联系白班客服」。
- 后勤号码、投诉号码及投诉时段一并返回，时段外投诉号码置空并带提示文案。

客户端不参与时段判断。

## 10. 领域规则的实现约定

下列默认值让 P0 能写完。产品若改规则，只改变配置或一处领域服务，不改表。

| 主题 | 实现 |
| --- | --- |
| 购卡绑定门店 | `membership.store_id` 取下单时门店。无改店接口 |
| 不可停卡 | 无暂停状态。资格取消只用 `REVOKED` |
| 不退款 | 买了不能退。小程序和管理端都没有退款。退款接口直接拒绝 |
| 限量 | `stock_total` 非空即限量。可售 = 总量 − 已售 − 占用 |
| 大会员解锁 | `unlock_type=CUMULATIVE_DAYS`，天数跨所有未作废会员区间合并 |
| 连续月卡解锁 | `unlock_type=CONSECUTIVE_DAYS`。从今天向前，会员区间不能断日。个人中心「还需 N 天」与卡列表锁定文案调用同一个 `MembershipProgressService` |
| 陪伴天数 | `今天 - registered_at`。`registered_at` 是人脸入库成功时间，与是否购卡无关 |
| 单次卡 1 天 | 默认支付成功时刻起 24 小时，卡种上 `duration_mode` 可改为自然日结束 |
| 未过期再买 | 默认从该店当前最大 `end_at` 往后顺延；已过期则从支付成功时刻起算 |
| 通卡 | `cross_store=0`。为 1 时验脸开门只校验用户存在任意有效通卡权限，不再比对门店。一期种子数据不启用 |
| 注册完成 | `register_status=ACTIVE` 且 `user_face.status=ENROLLED`。会员编号、陪伴天数从这一时刻起算 |
| 在线人数 | 该店 90 分钟内成功开门的去重用户数。仅有效会员接口返回数字，其他人返回 `locked=true` |
| 灰色卡点击 | 接口已给出 `purchasable=false`。前端照常可点，只展示 `lockText`，下单接口同样拒绝 |
| 带人扣天数 | 表留 `membership_day_adjust`。P0 不做自动扣减，由管理端记违规时手工扣 |

连续天数与累计天数不要在用户表里做唯一真源。用户表可以放冗余字段做展示缓存，会员区间一变就重算。

## 12. 数据设计

### 12.1 约定

- 引擎 InnoDB，字符集 `utf8mb4`，排序 `utf8mb4_0900_ai_ci`。
- 主键 `BIGINT` 雪花，API 以字符串传输。
- 每张业务表有 `created_at`、`updated_at`。
- 配置类数据用 `deleted` 逻辑删除。订单、支付、进店流水、核销流水不做逻辑删除。
- 状态字段用 `VARCHAR` 枚举名，不用魔法数字，例如 `PENDING`。
- 外键在应用层保证。数据库只建索引，避免支付回调批量写入时被外键锁拖住。高风险关联（订单与支付单）用唯一索引保证。

| `member_no_seq` | 会员编号序列 | P0 |
| `store` | 门店 | P0 |
| `store_phone` | 分时段电话，一行一个号码 | P0 |
| `store_guide` | 指引步骤 | P0 |
| `banner` | 首页运营位 | P0 |
| `notice` | 公告 | P0 |
| `agreement` | 协议及版本 | P0 |
| `card_product` | 卡种 | P0 |
| `trade_order` | 购卡、购课订单 | P0 |
| `payment` | 微信支付单 | P0 |
| `membership` | 会员权限区间 | P0 |
| `membership_day_adjust` | 扣天数、作废留痕 | P1 |

## 15. 微信支付

使用 API v3、小程序 JSAPI。

1. 统一下单字段：`appid`、`mchid`、`description`、`out_trade_no`（订单号）、`notify_url`、`amount.total`（分）、`payer.openid`。
2. 用官方 SDK 生成 `timeStamp`、`nonceStr`、`package`、`signType`、`paySign` 给 `requestPayment`。
3. 回调验签、解密资源、核对金额与订单号。金额不一致则标记异常并告警，不履约。
4. 应答微信要求的成功 JSON，处理失败返回 5xx 以便微信重试。重试靠 `transaction_id` 唯一键吃掉。
5. 不接退款。购买完成后不向微信发起退款，也不截断会员时间。

本地开发用内网穿透把回调打到本机，或在 test 环境支付后依靠主动查单 `查询订单 API` 履约。查单与回调调用同一个履约函数。

## 16. 闸机

闸机认脸，不扫二维码。主系统不绑定某一家厂商的 SDK，对人脸能力定义两个端口：

| 端口 | 调用方向 | 作用 |
| --- | --- | --- |
| `FaceVendorPort.enroll` | 本系统 → 厂商 | 注册时把照片和会员编号入库。失败则注册不成功 |
| `FaceVendorPort.revoke` | 本系统 → 厂商 | 停用用户时删除厂商侧人脸。本期可先留接口 |
| `POST /api/gate/v1/verify` | 闸机或适配进程 → 本系统 | 厂商已经比对成功，本系统只判断该不该开门 |

```
小程序上传正脸
  → COS 私有保存
  → enroll 到厂商（模板在闸机或厂商云）
用户到店
  → 闸机摄像头比对
  → verify：带上会员编号或 vendorFaceId
  → open=true 时继电器开门
```

厂商如果只能用 SDK、不能发 HTTP：门店内放一个适配进程，负责 SDK 入库和把识别结果转成 `verify`。适配进程不保存会员，不连 MySQL。语言随 SDK 走。它挂了只影响那一家店的门，不影响购卡。

本系统保存的是照片和 `vendor_face_id`，不自研识别算法，也不在业务库里存特征值。照片按生物识别信息控制权限，见第 6 节。

设备由总账号登记。未登记或停用的 `device_sn` 一律 `open=false`。心跳超过 3 分钟，设备列表标离线。一期只做列表，不做短信告警。门店账号能看到本店设备在线状态。

## 17. 并发、定时任务与一致性

| 点 | 做法 |
| --- | --- |
| 超卖 | 第 12.3 节条件更新 |

## 18. 日志、监控与备份

每条请求生成 `traceId`，写入响应体和日志 MDC。支付回调、验码、履约用同一 `traceId` 无法串联时，用 `orderNo`、`deviceSn` 作为业务检索字段。

日志级别：

- 验码结果、支付状态变更：INFO，不打印完整回调报文中的敏感字段。完整报文进 `payment.raw_notify`，库表权限收紧。
- 外部 HTTP（微信手机号、人脸入库、微信查单、COS）失败：ERROR，带耗时。不打印照片内容。

指标（一期用 Spring Boot Actuator，只监听内网）：

- 验码耗时与 `open=false` 比例
- 支付回调失败次数
- 待支付订单堆积
- 闸机心跳丢失

告警可以先做到日志平台检索。P0 至少保证：磁盘、MySQL、Redis、进程存活有云监控。

备份：MySQL 每日全量，binlog 保留 7 天。Redis 只放令牌和防抖，丢失后用户重新登录即可，进店不依赖 Redis 里的凭证。COS 开启版本控制，人脸目录和指引图都要能找回。

## 20. 开发规范

- 分支：`main` 可发布，功能在 `feat/*`。

| 灰色卡 | 可点开说明，不可下单 |
| 再次登录 | 手机号已注册且人脸已入库则直接进入，不重复拍摄 |

仍缺产品结论、因此不做死的交互：设置页里的注销字段、学生认证折扣规则、好评赠卡赠送天数、失物表单全部字段、支付成功页除状态外的营销文案。接口用空列表和明确错误码，不用假数据顶上。

## 23. 风险与对策

| 风险 | 对策 |
| --- | --- |
| 闸机只能用厂商 SDK | 门店适配进程负责入库和把识别结果转成 verify，业务库不变 |
| 人脸入库失败 | 注册状态停在 NEED_FACE，不发会员编号，闸机没有这个人 |
| 门店账号越权 | 服务端按令牌里的 storeId 过滤，单测覆盖跨店请求 |
| 微信支付回调延迟 | 前端回页面即查单，查单与回调整同一履约 |
| 一个商户号导致收银台不显示单店名称 | 支付描述写店名。若品牌要求收银台标题逐店不同，再开服务商模式，启用 `store.mch_id` |
| 小程序主包超限 | 分包和外置图片从第一天就执行 |
| 连续天数算错导致卡卖不出去或提前卖出 | `MembershipProgressService` 单测覆盖断档、当天到期、多店区间 |
| 竞品文案被写进仓库 | 评审种子数据和前端常量 |

# 闸机对接开发设计

协议字段以 `需求/闸机对接.md` 为准。代码已按本文接上，还没用实机走过。本机没有闸机时，管理端「模拟验码」仍走旧 HMAC。

当前实现和最初条文有两处差别：正脸在购卡确定门店后才下发，没买会员不会进闸机；换脸用 `editUser` 覆盖同一会员编号，不另发 `delUser`。

厂商闸机自己认脸。我们把正脸和会员到期时间下发给闸机，闸机认出人之后再问我们能不能开门。第一期用 WebSocket。MQTT 先不接。

## 1. 现有代码怎么处理

这些规则已经在 `GateService` 里，对接时继续用，不重写判断：

- 用会员编号找人。未注册、没有已采集人脸、设备停用，都不开门。
- 该店没有未过期会员，返回会员无效。别的店有会员，返回非本店会员。
- `cross_store=1` 的会员不比对门店。种子数据不要打开这个开关。
- 是否开门看服务端收到请求时的 `end_at`。
- 同一人、同一闸机、15 秒内第二次成功不再插入第二条成功流水，仍然开门。
- 课时码不开门。
- 进店记录按门店数据范围给管理端看。门店账号看不到人脸原图。
- 在线人数仍按成功进店去重。

这些要换掉：

- `POST /api/gate/v1/verify` 和 `POST /api/gate/v1/heartbeat` 是我们自己的 HMAC 协议。厂商闸机不会调用。新接口稳定后停用这两个地址。管理端「模拟验码」改成调用同一套开门判断，用来在没有闸机时验收。
- 注册时的 `MockFaceVendor` 只检查照片大小。正式下发改成向闸机发 `addUser`。照片仍然只收相机拍的一张正脸，不接另一家人脸云厂商，也不配人脸云密钥。
- 设备号现在自动生成 `SN{id}`。总账号改为填写闸机屏幕上的真实设备号。

## 2. 本期必须做

| 能力 | 协议 | 接到现有业务 |
| --- | --- | --- |
| 闸机上线 | `declare`、`ping` / `pong` | 用设备号匹配已登记闸机。`ping` 更新 `last_beat_at`，超过 3 分钟仍算离线 |
| 开门 | `POST /api/v1/verify_user` | 复用现有会员判断。`Result`：`0` 开门，`1` 已过期，`3` 未注册、非本店、设备停用 |
| 成功记录 | `POST /api/v1/record/face` | 幂等写入进店记录，响应必须 `Result: 0` |
| 陌生人记录 | `POST /api/v1/stranger` | 同样必须 `Result: 0`。过期会员补一条未开门记录 |
| 下发人脸 | `addUser` | 注册照片校验通过后，下发到该会员所在门店的闸机 |
| 改到期或换脸 | `editUser` | 购卡、续期、团购发卡改 `id_valid`；更换人脸改 `face_template` |
| 删除人脸 | `delUser` | 更换人脸成功后，从闸机去掉旧照片对应的人；账号侧没有停卡，不因为退款删人 |

`user_id` 用 9 位会员编号。不要用 `DL` 开头。

`id_valid` 用该闸机所在门店、这名会员当前有效期的 `end_at`，格式 `yyyy-MM-dd HH:mm`。还没有有效会员时，写成当前时间，避免闸机断网后把未购卡的人放进去。空字符串表示永久，不要这么传。

在线验证的 `Content.is_upload_record` 返回 `0`，通行流水在验证接口里写。记录接口若仍被调用，按「设备号 + 识别时间 + 会员编号」去重。

HTTP 响应是厂商的 `{Result, Msg, Content}`，不走现有 `{code, message, data}`。`Content` 用对象，不用字符串。

WebSocket 路径定为 `/ws/gate`。下发指令必须带外层 `cmd=to_device`。`declare` 和 `ping` 不带这层，也不要回复 `declare`。

## 3. 建议加上

下面几项不在厂商的「最少接口」里，但对这套 24 小时无人店有用。建议和本期一起做。

1. **下发队列。** 闸机不在线时，注册仍然发会员编号，任务记成待同步。闸机下次 `declare` 之后按顺序补发。`addUserRet.code` 为 `0` 才标成已同步。失败保留原因，可在管理端重试。照片小于 32 字节的规则保留，这种不入队。
2. **只下发到本店闸机。** 会员买的是哪家店，照片就只进那家店的闸机。这样断网时，别的店的闸机本地也认不出这个人。通卡以后如果打开，再下发到全部门店。
3. **陌生人可以落库。** `door_log.user_id` 现在是非空，未匹配的识别被丢掉。改成可空，记下设备、时间和「未开门」。总账号能看到陌生人次数。在线人数仍然只统计成功进店。
4. **连接后对时。** 每次 `declare` 成功后发 `setTime`，用服务器的北京时间。识别时间、签名时间都靠设备时钟。
5. **同步状态给管理端。** 每台闸机、每个会员显示待同步、已同步或失败原因。门店账号能看本店，不能改设备号。
6. **小程序提示未同步。** 已登录但本店闸机还没确认人脸时，「我的」显示「人脸正在同步到门店闸机」。不影响购卡。

建议放在实机联调之后、正式上线之前：

1. **签名。** 用 `setHttpToken` 下发 token，校验 HTTP 头和 `declare` 里的 `iot_signature`。时间窗口按厂商建议先用 1 分钟，随机数放 Redis 防重放。本机 `local` 可以关闭签名，方便没有闸机时用脚本测。
2. **识别间隔。** 用 `setRecognitionInterval` 设成 15 秒，和现有防抖一致，减少闸机连打验证接口。
3. **关闭「在线验证失败仍放行」。** 用 `setOnlineVerifyFailurePass` 明确关掉。网络超时必须不开门。

可以做，但不放进第一期：

| 能力 | 原因 |
| --- | --- |
| 远程开门 `setDoor` | 人脸失败时店员救急有用。要总账号或本店账号、写 `admin_audit`，避免变成后门 |
| 识别置信度、距离、活体 | 现场光线和误识率确定后再调，先在闸机屏幕上设 |
| 按周通行规则 | 现在只看会员 `end_at`，不需要周计划 |
| 读回闸机人员 | 对账用。队列和同步状态稳定后再做 |
| MQTT | WebSocket 在单台服务器上够用。多机部署时再评估 |

明确不做：在线比对（要把照片发给我们做人脸算法）、密码开门、二维码开门、指纹、体温、健康码、广告、人证访客。课时码继续不能开闸机。

## 4. 业务流程

1. 总账号登记闸机：真实设备号、名称、所属门店。
2. 闸机对接方式选开发者，服务器填我们的地址，长连接填 `ws://域名:端口/ws/gate`，打开「识别后在线验证」，可通行人员选已注册用户。
3. 闸机连接后发 `declare`。设备号未登记则丢弃后续指令，并在日志里记一次。已登记则回复后续 `pong`，更新在线时间，接着对时、补发队列。
4. 用户上传正脸。照片过了大小检查就发会员编号。这时还没有门店，照片只留在服务端。
5. 购卡、续期或团购发卡成功后，给这家店每台启用中的闸机生成下发任务。第一次是 `addUser`，之后只改到期时间或照片。
6. 用户到店。闸机本地认脸，调用 `/api/v1/verify_user`。有效会员 `Result=0` 并写成功流水。
7. 更换人脸：新照片入队 `editUser`，覆盖同一会员编号。新任务成功后，旧的 `user_face` 标成 `REPLACED`。失败则闸机上仍是旧脸。

一台店有多台闸机时，每台各有一条任务。有一台失败，会员仍可走已经同步成功的那一台。

## 5. 模块

都放在现有 `code/server` 里，不另起进程。

| 部分 | 职责 |
| --- | --- |
| `VendorGateHttpController` | `/api/v1/verify_user`、`/api/v1/record/face`、`/api/v1/stranger`。只返回厂商 JSON |
| `GateSessionHub` | 保存设备号到 WebSocket 会话。下发前检查设备在线 |
| `GateCommandSender` | 组 `to_device` 信封，等待对应 `to` 的回复，超时记失败 |
| `GateSyncWorker` | 扫待同步任务。设备在线就发送，按 `addUserRet` / `editUserRet` / `delUserRet` 的 `code` 更新任务 |
| `GateAccessService` | 从现有 `GateService.verify` 抽出开门判断，供厂商接口和管理端模拟共用 |
| 照片编码 | jpg、不超过 300KB、边长不超过 1280。Base64 带 `data:image/jpeg;base64,`，再做 URL 编码，放入 `face_template` |

长连接会话在本进程内存里。第一期部署一台云服务器，闸机都连这一台。下发任务进数据库，进程重启后可以补发。防抖和签名随机数继续用现有 `GateState`：本机内存，`dev` / `prod` 用 Redis。

### 数据

`gate_device` 增加：

- `token`：签名密钥，可空。总账号可重置。
- `firmware`：最近一次 `declare` 的版本名，便于排查。

`device_sn` 改为总账号录入，保持唯一。`secret` 列留给旧模拟验码，新协议改用 `token`。停用旧接口后不再展示 `secret`。

新增 `gate_sync_task`：

| 列 | 说明 |
| --- | --- |
| `id` | 雪花 |
| `device_id` | 哪一台闸机 |
| `user_id` | 哪个会员 |
| `cmd` | `addUser`、`editUser`、`delUser` |
| `status` | `PENDING`、`SENT`、`OK`、`FAILED` |
| `attempts` | 已尝试次数 |
| `last_error` | 闸机返回的 `msg`，或超时 |
| `created_at` / `updated_at` | 北京时间 |

同一设备、同一用户、同一种 `cmd`，未完成的只保留最新一条。续期两次就只下发最后的到期时间。

`door_log` 调整：

- `user_id` 改为可空。
- 增加 `recog_time`、`pass_status`。
- 唯一约束：`device_sn + recog_time + member_no`。陌生人的 `member_no` 用闸机传来的 `user_id`（常见是 `F1000001`），过期的人用 `real_user_id`。

`user_face.vendor_face_id` 继续存我们下发的会员编号，方便和旧查询兼容。同步结果以 `gate_sync_task` 为准。

## 6. 管理端

总账号：

- 登记、停用闸机，填写真实设备号。
- 看在线、固件、待同步人数、失败原因，可对本店失败任务重试。
- 进店记录增加未开门和陌生人。
- 模拟验码改为输入会员编号，走 `GateAccessService`，不走 HMAC。

门店账号：

- 只看本店闸机是否在线、本店进店记录、本店同步失败。
- 不能改设备号，不能看密钥和人脸原图。

## 7. 开发计划

每步的完成标准达到后再做下一步。本机没有闸机时，用单元测试和一段 WebSocket 脚本模拟 `declare`、`ping` 和 `addUserRet`。

### 步骤 1：协议入口

1. 三个 HTTP 接口返回厂商 JSON，未知设备号返回 `Result: -2`。
2. WebSocket `/ws/gate` 接收 `declare` 和 `ping`，已登记设备回复 `pong` 并更新 `last_beat_at`。
3. 总账号把设备号改成手工填写。

完成标准：脚本连上后，管理端 3 分钟内显示在线。未登记设备号调用验证接口得到 `-2`。

### 步骤 2：开门和流水

1. `verify_user` 调用现有开门判断。有效会员 `Result=0`，`is_upload_record=0`。
2. 过期返回 `1`，未注册和非本店返回 `3`。
3. 记录接口幂等，失败也返回 `Result=0`。
4. 陌生人写入 `user_id` 为空的未开门记录。
5. 15 秒防抖保持。

完成标准：沿用现有单测场景：未购卡不开门，过期不开门，A 店会员在 B 店不开门，15 秒内只有一条成功流水。课时码不开门。

### 步骤 3：下发队列

1. 照片编码。
2. `gate_sync_task` 和补发。
3. 注册、购卡、续期、团购、换脸写入队列。
4. 只推本店启用中的闸机。未购卡的 `id_valid` 用当前时间。

完成标准：闸机离线时注册仍能拿到会员编号，任务为待同步。模拟闸机上线后任务变为已同步。续期后模拟闸机收到新的 `id_valid`。换脸失败时任务保持失败，旧脸状态不变。

### 步骤 4：管理端

1. 设备号手工录入、在线、同步状态、重试。
2. 进店记录显示未开门。
3. 「我的」在本店还有待同步任务时提示正在同步。
4. 模拟验码改走开门判断。

完成标准：总账号能登记一台闸机并看到同步失败；门店账号看不到别的店，也看不到密钥。

### 步骤 5：上线前

1. `setTime`。
2. 签名和 token。`local` 可关。
3. 识别间隔 15 秒，关闭验证失败放行。
4. 停用 `/api/gate/v1/verify` 和 `/api/gate/v1/heartbeat`。
5. 用一台实机走完：注册、购卡、进店、到期进不去、续期又能进。

完成标准：实机在线验证 5 秒内返回；断网后续期之前，未购卡用户不能被本地放行；记录接口返回非 0 时，闸机不会把同一条记录无限打进来。

## 8. 不做的部署假设

开发阶段后端继续用 `local`。闸机要访问的是局域网或已备案的 HTTPS 域名，本机 `127.0.0.1` 闸机访问不到。实机联调时把后端跑在闸机能访问的地址上，再用步骤 5 验收。
